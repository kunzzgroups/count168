输入测试 / Input test

这个页面用来定位「删除键延迟」到底发生在哪一层。不涉及账号，不会提交任何东西。
This page finds out which layer eats the delete key. No account, nothing is submitted.

  1. 在每个框里用同一个输入法连续输入 5 个字母（例如 abcde）。
  2. 然后连按删除键 6 次，一边按一边看下面数字。
  3. 按完点最下面的「重置」再测下一个框；最后把整页截图发给客服。

A · 什么都没有的输入框

最纯净：没有任何框架、没有任何改写文字的逻辑。如果这个框也卡/也丢删除，问题就不在我们的代码里。

B · 每次按键都改写文字的输入框

模拟我们以前的写法（每次按键把内容重写一遍）。预期会看到丢字/卡顿 —— 这条是"旧写法确实有问题"的对照。

C · 现在的写法（原生监听，不改写）

和 App 里登录页/搜索框现在用的同一套做法（只读 DOM 的值，从不回写）。

读法：「删除到达页面」若明显小于「你按了几次删除」，说明那几次删除被输入法/WebView 吃掉，页面根本没收到 —— 那不是页面能修的。
